# 90 · 不可恢复的原服黑盒

**原版运营服务器已停服。抓包不可行。** 下面这些内容既不在客户端里，也不在任何可获得的报文里，
因此本档案**不给出**它们的算法或取值——只列出「缺什么」和「为什么缺」。

把它们标出来，是为了防止后续实现把这些空位当成已复原的协议。

## 9.1 完全没有样本的报文

| 动作 | 缺什么 | 客户端能证明的部分 |
|---|---|---|
| `versionPlus.check` | 原服响应取值、`result` 的真实语义、下载服务器行为 | 请求字段与响应字段名 |
| `menu.notice` | 公告正文与 `notice` 字符串的编码细节 | 字段名与「它是一个 JSON 字符串」 |
| `account.index` | `token` / `user_auth` 的产生与校验、真实服务区列表 | 字段名与客户端消费路径 |
| `user.login` | 完整响应报文；`cmn` 各表的真实内容 | 全部被读取的字段名 |
| 其余 236 个 `do=` 动作 | 全部请求/响应的真实取值 | 字段名、调用点、响应交给哪个模型 |

本档案给出的是**客户端消费契约**，不是服务端报文格式的完整定义。
服务端完全可以发送契约之外的字段而客户端毫无反应。

## 9.2 服务端算法

- 酒馆招募池、概率、保底计数、随机数策略；
- 副本敌方组队、AI、伤害与触发公式、动作流生成；
- 关卡掉落概率、星级评价、经验/金币收益、体力扣减、次数限制、奖励幂等；
- 玩家升级与成长公式、章节与宝箱解锁判定；
- `token` / `user_auth` 的签发与校验、账号服与游戏服的信任关系；
- `server_params` 的内容与用途（客户端只是原样回传）；
- 排行榜计算、公会战与跨服战的匹配和结算；
- 支付订单校验、发货与补单逻辑；
- 风控、封禁、异常检测、并发顺序与数据库事务边界。

这些以后可以在重建服务端里**重新设计**，但必须标注为「重建设计」，
不能标注为「原版算法复原」。

## 9.3 静态提取侧的空缺

以下是**方法**造成的信息缺失，不是原服黑盒，但同样需要知道：

| 空缺 | 原因 | 影响 |
|---|---|---|
| 未解析的调用点 | 重建 JS 中 `TODO_BYTECODE` 区域、动态回调、条件分支 | 见 [endpoint-index.md](endpoint-index.md) 的「无调用点的动作」 |
| 未解析的请求字段 | 参数由调用方整体构造后传入，未在调用点可见 | 端点页标注「静态提取未解析到显式字段」 |
| 未解析的响应字段 | 响应处理器只更新 UI 或状态走 `cmn` | 属正常结构，不是缺失 |
| 运行期拼接的 `do=` | 由变量或用户输入拼出的动作名 | 静态字面量已全部纳入 244 个动作 |
| 原生层行为 | `xs.Utils.Net.reqAsync` 以下是 C++/JNI | 只能看到它的入参与回调 |

## 9.4 证据等级低但常见的误读

| 误读 | 实际 |
|---|---|
| 「响应根字段有 93 个，说明协议很小」 | 根字段少是因为状态走 `cmn`；`cmn` 才是主体 |
| 「`add_list` 返回了奖励，玩家就拿到了」 | `add_list` 只驱动展示；持久化必须走 `cmn` |
| 「`fight_info` 的动作流就是战斗过程」 | 它只是播放数据；权威结果在 `fight_result` |
| 「错误码表就是错误含义表」 | 客户端只做字符串比较，服务端 `msg` 才是文案 |
| 「`pk_id` 就是配置 ID」 | `pk_id` 是玩家实体主键，与静态配置 ID 不同 |
| 「`ignoreRandEvent` 会发给服务端」 | 它在序列化前被删除，是纯客户端开关 |
| 「`/auth/register` 是原版接口」 | 本重建工程新增，原版走边锋 SDK |

## 9.5 结论

本档案能支持的工作：

1. 用客户端**真实会读**的字段形状构造兼容响应；
2. 用 244 个端点与 392 个调用点核对覆盖度，找出还没实现的业务面；
3. 把「哪些是原版事实、哪些是重建设计」分清。

本档案**不能**支持的：声称复原了原版服务端行为、数值或平衡。
